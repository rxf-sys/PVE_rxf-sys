### Zu Punkt 7 — File-Level-Restore

```
proxmox-backup-restore-image: not correctly installed
```

Das Paket liefert das Kernel/Initramfs-Image, mit dem PBS einzelne Dateien aus
einem Backup extrahiert. Ohne funktionierendes Paket schlägt der
Datei-Restore fehl — und zwar erst dann, wenn man ihn braucht.

```bash
apt install --reinstall proxmox-backup-restore-image
pveversion -v | grep restore-image
```

Danach einen Probe-Restore einer einzelnen Datei fahren, siehe
[../06-backup/restore-procedures.md](../06-backup/restore-procedures.md).

## 3. Backup-Ausfall 12.–16. Juli 2026

Fünf Nächte in Folge schlug der vzdump-Job fehl:

```
could not activate storage 'pbs': pbs: error fetching datastores -
500 Can't connect to 192.168.2.209:8007 (No route to host)
```

Ab dem 17.07. wieder grün, seitdem durchgehend `OK`. Die Benachrichtigungen
liefen über den Matcher `to-strato`, die Meldungen sollten also zugestellt
worden sein.

**Offen:** Ursache ist nicht geklärt. „No route to host" deutet auf die PBS-VM
oder deren Netzwerk, nicht auf den Datastore. Zwei Dinge lohnen sich:

1. Einen Uptime-Kuma-Monitor auf `192.168.2.209:8007` legen, damit ein
   PBS-Ausfall auffällt, bevor fünf Backups ausfallen.
2. `startup: order=1` der PBS-VM gegenprüfen — wenn PBS nach einem Host-Reboot
   zu spät kommt, läuft der 02:00-Job ins Leere.

## 4. Fehler im Audit-Skript

Drei der sechs WARN waren keine echten Befunde, sondern Bugs. Alle behoben in
`doc-audit.sh` (Commit „Fix doc-audit.sh"):

| Falschmeldung | Ursache |
|---------------|---------|
| „Enterprise-Repo aktiv" | rekursives grep traf `.disabled`-Dateien, die apt nie liest |
| „Reboot ausstehend" | Vergleich von Kernel `7.0.14-8-pve` mit Paketname `…-pve-signed` |
| „Backup 201 veraltet (76d)" | `exclude 201` wurde nie geparst — awk kennt `\s` nicht |

Der dritte Bug wog am schwersten: Dieselbe `\s`-Klasse steckte auch in der
Prüfung von `enabled` und `schedule`, weshalb der vzdump-Check über einen
Default-Wert auf PASS ging statt über den echten Zustand.

Zusätzlich behoben:

- `authorized_keys` gab bei Zeilen ohne Kommentar das Key-Material aus — genau
  so landete der private RMM-Schlüssel im Report.
- Die Redaktion kannte nur PEM-Header, nicht den base64-Header eines
  OpenSSH-Private-Keys.
- `aa-status --summary` existiert nicht; die Sammlung druckte den Hilfetext.

Neu ergänzt: zwei Checks, die prüfen, ob je Guest ein Regelsatz existiert und
dort `enable: 1` gesetzt ist. Genau der Befund, den das erste Audit übersehen
hat.
